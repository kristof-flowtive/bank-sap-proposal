01 — Understanding

What you're solving for

You receive bank statements as JSON. Today, those entries make their way into SAP through manual handling — a process that's slow, error-prone, and doesn't scale. You've already identified the shape of the right solution:

  • Low-code, not custom-coded. Make.com or Power Automate so your team can read, audit, and modify the workflow.
  • OpenAI for data mapping. Field-level intelligence so transactions are categorized and shaped correctly for SAP — even when bank schemas vary.
  • No databases, no servers. Existing cloud tools only. No infrastructure for your team to babysit or budget for.
  • Reliability over price. A solution that works on day 365 the same way it worked on day 1.

This proposal is built around those constraints. Every choice below maps directly to one of them.

03 — The intelligent layer

How OpenAI handles the messy bits

Banks don't follow a single schema. Field names drift. Reference codes vary. Some descriptions are cryptic. This is where rule-based mappers break — and where a small, well-prompted LLM call shines.

  • → Field reconciliation: Maps txn_amt, amount, value all to SAP's expected key.
  • → GL account suggestion: Reads the description, suggests the right General Ledger code based on rules you provide.
  • → Confidence scoring: Returns a score with each entry. Below threshold → review queue.
  • → Schema-locked output: Uses structured JSON output so SAP never receives a malformed payload.
openai_mapping.json 
// Bank JSON (input)
{
  "txn_id": "BX-44120",
  "txn_amt": -2450.00,
  "desc": "AWS HOSTING NOV",
  "date": "2026-04-30"
}

// → OpenAI structured output
{
  "sap_doc_type": "KZ",
  "posting_date": "2026-04-30",
  "amount": -2450.00,
  "gl_account": "6420 — IT Hosting",
  "vendor": "Amazon Web Services",
  "reference": "BX-44120",
  "confidence": 0.97
}

06 — Why this approach

Reliability is the whole point

You said it directly: not the cheapest, the most reliable. Here's what that looks like in practice.

No servers to fail

Make.com and OpenAI are managed services with multi-9s uptime. You don't patch them. You don't restart them. They just run.

Every run is auditable

Make.com logs each scenario execution with full input/output history. When something looks off, the answer is one click away — not a server log dive.

Your team can own it

No bus factor on me. The scenario is visual, the prompt is plain English, the docs are short. Your team can extend it without calling me back.

Failure is graceful

Bad data goes to a review queue, not into SAP. Confidence below threshold? Human checks first. Nothing posts that shouldn't.

Easy to extend

Need to add a second bank? Another SAP module? Different routing rules? Each is a small additive change to the same scenario.

Predictable cost

Both Make and OpenAI scale linearly with usage. No infrastructure surprises. You'll know the running cost from week one.
